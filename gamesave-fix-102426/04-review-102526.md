## 2. Defects found (most severe first)

Line numbers are the delivered `Game-Code/.../DatabaseSaver.cs` unless another file is named.

### R1. An older save's late acceptance overwrites the device copy of the newer unsent save. HIGH

`SendLoop` persists *the item whose request just finished*, not the newest record: lines 452–453
(`item.sent = true; PersistLocal(item)`), 469–470 (dropped) and 409–410 (recovered save dropped).

Scenario: checkpoint A is recorded and written to the slot; its request is slow. Checkpoint B is
reached before the answer → B is recorded and written to the slot (unsent). A's 201 arrives → the
slot is overwritten with A (sent). The network then drops, B's sends fail, the student reloads or
the profile resets → the next launch reads A (sent), finds nothing to send, resumes from A. B is
gone. The window is one request's duration plus the whole retry period of B.

Fix: after a request, persist `newestSave` when it is not the item (or skip persisting a stale
item; the slot already holds the newer record). Same in the two "dropped" paths. One test: A held
by the fake service, B recorded, A released and accepted, relaunch → B is found and sent.

### R2. START GAME resumes the menu's cached answer, however old. HIGH (server rollback)

The fetch runs once per launch (line 805 exits for good once `serverLatest` is set) and START reuses
it (626–631). The original code fetched again at START.

Scenario: a tab sits at the main menu (fetched at sign-in); the student plays elsewhere, saving
newer progress; later presses START in the old tab → the stale save is resumed, and the next
checkpoint writes it to the service with a newer timestamp. The service's newest is now behind.
Tabs do stay open for days (the heartbeat tabs in the week review).

Fix: remember when the answer arrived; at START, if it is older than about a minute, fetch again
(the normal flow, menu → START within seconds, still makes one request; the device-copy fallback
already covers a fetch that fails). Test: a second START after an aged answer makes a request.

### R3. The reconcile after a device-copy resume compares against the launch-time copy, not the progress since. HIGH

In `StartFromSave`, `local` is read once (630–634) and never refreshed (653 only if null). When the
service answers later, `ServerNewerThan(serverLatest, local.saved_at)` (658) looks at the copy the
game *started* from, and `chosen` is applied in place (663–669).

Scenario: last night the student played at home (the service holds S_home). Today the service is
unreachable at launch; the game resumes from this device's older copy; the student plays ten
minutes (checkpoints recorded, unsent, all newer than S_home). The service comes back → S_home is
newer than the launch-time copy → it is applied in place: positions and quests jump back to last
night. The unsent ten-minute save is still sent, but the next checkpoint saves the rewound state as
the newest. The student loses the session and sees it happen.

Fix: decide against this device's newest progress at that moment (`LocalCopyFor(uid)` already
returns this launch's newest record); apply the service's save in place only when nothing newer
has been recorded since the resume. Test: resume from a copy, record a save, then let the service
answer with something in between → nothing is applied, the newer save is sent.

### R4. With no identity and no config at all, START GAME never proceeds. MEDIUM, decision needed

`StartFromSave` waits for `serverLatest` (631–650), which needs a valid id (`GameSaveManager.cs`
239) and a config (234). On a host page without `__mhsBridgeConfig` and without an identity
endpoint, the id is empty for ever and there can be no device copy either: the menu shows
*Loading your progress... waiting for your sign-in* indefinitely. The original fell back to the
built-in host, failed, and started a new game, so the game was playable (and unsaved) anywhere.

This is the brief's rules 1 and 7 colliding with "the game must run without StrataHub". The WebGL
template hand-off provides identity and config on other hosts, so a correctly set up standalone
page is fine; the case is a page with neither. Options: (a) keep waiting (strict; a developer's
local build without the template is stuck at START); (b) after N seconds with no identity source at
all (no bridge config and the identity endpoint says "not authenticated"), start a new game with
saving disabled and a visible line; (c) the same, but only when there is also no `state_load`
config, so a StrataHub page that is merely slow keeps waiting. Recommendation: (c), N ≈ 20 s.

### R5. A non-empty load answer whose newest record is unreadable counts as "no saves". MEDIUM (unlikely today)

`NewestIsASave` (`GameSaveManager.cs` 143) requires a scene name; without one the result is
Accepted with `hasSave = false` (456, `DatabaseSaver.cs` 842–854), `ChooseResume` returns null
(762–769) and START starts a new game (695–713). The brief's rule says only the literal `[]` may do
that. Today's service writes nothing that lacks a scene name, so this needs a malformed or foreign
document; but the outcome is the one the fix exists to prevent.

Options: treat an unreadable newest as a retryable failure (strict; a permanently malformed newest
then blocks the player), or ask for the last five and resume from the first readable one, starting
a new game only when the list is empty. Recommendation: the latter.

### R6. The recovered-save wait shows no reason or countdown, and two loops write one line. MEDIUM (rule 4)

While a recovered unsent save waits for the service's answer, `SendLoop` writes *Saving an earlier
checkpoint... checking the server* every second (401–404) with no reason, countdown or attempt;
the fetch's countdown is hidden unless START is running (867–868). After START the two texts
alternate every second; with a device copy, *Using the progress saved on this device...* (645) is
overwritten within a second. T13 uses a *sent* copy, so none of this is tested.

Fix: one owner of the line while a fetch is retrying (the fetch's countdown, shown whenever a
player is waiting on it or a recovered save is); the recovered-save text becomes the countdown's
first line. Test: relaunch with an unsent copy and the service down, assert the line.

### R7. During a load retry's request the countdown freezes at "1 s". MEDIUM-LOW

`FetchLoop` sets no text before `LoadLatest` (832–836), unlike `SendLoop` (437–438). On a
black-holed connection the student watches *Retrying in 1 s (attempt 2)* for up to 45 s. Fix: set
*Loading your progress... (attempt N)* before the request when the line is visible.

### R8. A sent device copy beats the service's newest on a zero-tolerance comparison of two device clocks. MEDIUM-LOW, decision needed

`ChooseResume` 779–784 with `DeviceNewerThanServer` (1187–1191): when this device's *accepted*
copy carries a later `saved_at` than the service's newest, the copy wins. Both times come from
device clocks when the saves have metadata, so a device whose clock runs minutes fast resumes its
own older progress after the student played on another device, and the next checkpoint overwrites
the newer progress. The case the rule serves (the service returning an older save than one it
accepted) has no observed instance.

Recommendation: for a copy the service accepted, trust the service's answer (drop the branch), or
require a margin of several minutes. The unsent-copy comparison (772–777) has the same clock
exposure but protects real unsent progress; keep it.

### R9. The device-storage budget is not enforced, and a failed move-aside blocks the slot write. LOW-MEDIUM

Up to 8 pending copies of other players (constant `MaxPendingKeys`, line 101) at up to 256 KB each
(`LocalSaveMaxChars`, 86) plus the slot plus the logger's cache (512 KB) can exceed WebGL's 1 MB
PlayerPrefs cap. `AddPendingKey` runs inside the same `try` as the slot write (959–968): when it
throws, the slot is not written, `slotIsOurs` stays false, and every later write repeats the
failure, so that player's saves are never kept on the device, and the logger's cache writes start
failing too. Shared Chromebook during a service outage is the scenario.

Fix: move the move-aside into its own guard (on failure evict the oldest pending copy and retry
once); lower the caps (4 pending, 128 KB per record covers today's 45 KB saves three times over).

### R10. The alert canvas cannot fade in while game time is paused. LOW-MEDIUM, file outside the bundle

`UICanvasGroupFadeInOut.LerpCanvasGroupAlpha` advances with `Time.deltaTime`; a fade-in started
under `Time.timeScale = 0` (`TimeManager.PauseTime`, `TimeScaleManager`) first sets the alpha to 0
and then never moves, so a status set while the game is paused is invisible until it is unpaused.
The retry waits are real-time, so a countdown can run its course unseen. Pre-existing component
(the old two-second toast had the same flaw); one line (`unscaledDeltaTime`) in a fifth file, or a
note for the team.

### R11. A newer save recorded during a retry countdown waits the countdown out, and inherits its attempt number. LOW

`SendLoop` 480–483: the countdown is not interrupted when `newestSave` changes, so a checkpoint
reached right after an outage can wait up to 60 s for its first attempt although the service is
back; `saveAttempt` (436) and `delay` carry over, so its first line reads *attempt 7*. Fix: end the
countdown early and reset the counters when the item changes.

### R12. A second `DatabaseSaver` lives for one frame in every gameplay scene. LOW

The `SaveSystem` prefab is nested in both core-systems prefabs; the PixelCrushers `SaveSystem`
destroys the second object, but `Destroy` is deferred, so the duplicate's `OnEnable` and `Start`
run (183–210, 215–220). With this player's unsent record in the slot (service down) the duplicate
logs *an unsent save from an earlier launch was found*, starts a send loop, which starts a fetch,
which sends one load request whose coroutine then dies with the object; it also raises the shared
fade-in event. One stray request and a misleading log line per scene change during an outage; a
double record only if a checkpoint fires in that same frame. Fix: the same guard the logger uses
(a second instance does nothing), or defer `RecoverPendingAtLaunch` by one frame.

### R13. Frame gaps over one second reset the transition request. LOW, bounded

Both gates (1095; `GameLogger.cs` 1285) take a gap of more than a second between polls as a new
request. A hidden or throttled tab polls less often than that, so the five-second cap cannot fire
until the tab is visible again. It resolves on return; no permanent hang. A scene-change or
explicit "transition begins" signal would be the robust rule; not needed for this round.

### R14. Tests that claim more than they check. LOW

- T12 "starts a new game": the rig has no `TransitionSceneLoader` and the code uses `?.`, so the
  test only proves nothing was applied and the status cleared; the new-game start is unobserved.
- T13 "the countdown does not replace the device-copy line" uses a *sent* copy; R6 is untested.
- `AssertNoAuthInLogs` sees `Debug.*` only; `ConsoleLogManager.Instance` is null in the test scene,
  so a leak through `Print` could not be caught (there is none today).
- Nothing covers R1–R5, any scene change (`ResumeWith` through the Transition scene,
  `ApplyDataAfterSceneLoaded`), a 400 on a load, or `Retry-After`; `mhs_pending_index` is never
  cleared between tests.

## 3. Caveats to put in the documentation (not defects)

- **Where the device copy lives.** WebGL PlayerPrefs are stored under a path derived from the page
  URL's directory. On the StrataHub play page every unit shares it, so "the next unit's build sends
  the kept save" holds there. On a host that serves each unit from its own folder the units do not
  share it: a save left unsent at a unit transition waits until that unit's page is opened again.
- **Two devices, two clocks.** Every comparison between a device copy and a save with metadata is
  between device clocks. Same device, same clock: exact. Two devices minutes apart: R8 and the
  recovered-save check (406) can decide wrongly. Server-clock saves (older builds) get the 90 s
  allowance; device-clock saves get none.
- **A staff reset while a device holds a copy.** With the service reachable at launch, "no saves"
  plus a sent copy starts a new game, as intended. If the service was unreachable at launch and the
  game resumed from the copy, the later "no saves" answer does not pull the player out, and the next
  checkpoint writes the old progress back to the service.
- **A host without a save config** shows *Saving... waiting for the save service settings* on every
  checkpoint for as long as the session lasts (documented in `03`); it is the right behaviour for a
  misconfigured page, but the team should know it is a permanent line, not a toast.
- **A record made before the id is known** carries no `user_id` until the send loop fixes it; if
  the page closes in that window the next launch discards it. On StrataHub the id is known before
  the first checkpoint; elsewhere saving waits for the id anyway.

### V1. R4 does not fire on the page it was decided for. HIGH

`FetchLoop` checks the player id (920–931) before the config (933–954), so `noConfigSince` never
starts while the id is missing. On a page with neither identity nor config, the exact R4 case,
`ResolveUserId()` is null for ever, the loop shows *waiting for your sign-in* for ever, and START
never proceeds. The rule works only when an identity exists (the Editor's developer id, the
localhost page). Check 8 in `03` is therefore not true for a real page without the host's config,
and T24 keeps the identity so it cannot see this. Fix: decide "no load config for the grace
period" independently of the id (config check first); a page with config but no identity still
waits, as decided. T24 gets the no-identity case; a build served from a plain page is the on-site
check.

### V2. The refetch at START throws the known answer away. HIGH

714–720 null `serverLatest`; the wait loop (726–745) then resumes from the device copy at the first
failure, or waits at the menu when there is none. Scenario: the menu fetched last night's save
from the service at 8:00; the student presses START at 8:02; the save host is stalled at that
moment → the refetch fails → the game resumes from this device's older copy (or waits), although
it knew a newer answer two minutes ago; the first checkpoint then writes the older line as the
service's newest. In 1.1 START reused the answer. Fix: keep the aged answer as the fallback when
the refetch fails (it beats a copy the service accepted, as R8 already says; an unsent copy newer
than it still wins; a stale "no saves" is not acted on), and replace it only when the refetch
answers.

### V3. An unsent save of this launch is sent even when the service is known to hold newer progress. MEDIUM

The "service already holds newer progress → drop" check runs only for a recovered save
(`newestRecovered`, 458–484). A checkpoint recorded after a device-copy resume, or while a refetch
is pending, goes out unchecked; if the game has meanwhile applied the service's newer save in
place (766–777) or learned of it, the older record still overwrites it on the service. Needs a
second device or a stale tab, but it is the rollback class this fix exists for. Fix: apply the
check to any unsent item once `serverLatest` is known and newer (the game's own accepted saves
are never newer than a later record, so the normal path is unaffected). The second reader also
notes the policy consequence that stays: progress made offline from an older device copy is a
fork that cannot be merged with a newer save made elsewhere; the newest by time wins, and the
other line is shadowed. That is the decided behaviour, now stated.

### V4. Two writers during the first in-flight load with a recovered save. LOW-MEDIUM (rule 4)

Line 470 writes *Saving an earlier checkpoint... checking the save service* every second
directly while `fetchFailures == 0`, bypassing `FetchLineOwner`; START pressed during that first
request (up to 45 s on a black-holed host) has its *Loading your progress...* overwritten each
second. Fix: route it through the owner.

### V5. Toasts cut short. LOW-MEDIUM (rule 4)

(a) A recovered save dropped at 481 ends with `HideStatus()`, which can hide START's *Progress
loaded* toast within a second. (b) The no-config exit of `SendLoop` (432–438) hides START's
*Playing without saving* toast. Fix: those hides skip while a toast is up.

### V6. A page without a save service, with a leftover unsent record, waits the five-second cap at every unit transition. LOW

`SendLoop` exits on `noServiceConfig` but the record stays `newestSave`, so the gate (1302–1310)
waits and logs at every transition. Fix: the gate treats `noServiceConfig` as nothing unsent.

### V7. The `live` guard can be taken by the reference-less stray saver. LOW (developer flows)

`live = this` (268) is set before the asserts. The bare `DatabaseSaver` on the pause menu's Load
Button has no references and no `GameSaveManager`; in a scene not entered from the main menu
(Editor play from a unit scene) its `OnEnable` may run first, take `live`, throw, and leave the
real saver inert: no saves, no load, silently. Fix: a saver whose references are missing is never
`live`; `InitializeDataAfterSceneLoaded` also respects `isDuplicate`. The stray component should
still be deleted (first review, §4).

### V8. The pending index can list keys that are gone, which defeats the eviction retry. LOW

`AddPendingKey` deletes overflow keys before it writes the index; if the record write then throws
(quota) the index still lists them, `EvictOldestPending` "evicts" a key that no longer exists, the
retry fails, and the other player's unsent copy is dropped although space could have been freed.
`ReadRecord`'s delete of an unreadable record also leaves the index stale. Fix: evict until a key
that was present is gone; write the index first.

### V9. The no-config decision is made only by the fetch loop. LOW

In a scene opened directly (the Editor without the developer file) with an unsent record in
PlayerPrefs, `SendLoop` waits with *Saving... waiting for the save service settings* for ever,
because no fetch runs to decide `noServiceConfig`. Fix: one shared decision used by both loops.

### V10. Tests. LOW

T29 proves little (the duplicate was never subscribed to the first rig's event; its own event
raise and a direct `SaveGameToDatabase` call, plus "no load request appears when a duplicate meets

T23 passes because the load backoff (3 s) is shorter than the save backoff (5 s); a fake-service
mode that fails saves while answering loads makes it deterministic.

### V11. The fade helper is on the scene fader too. Note

`UICanvasGroupFadeInOut` is also on the scene fader prefab and the sandbox loader; both have
`fadeOnSceneLoad: 0`, so only their explicit fades change (they now run on real time). Say so in
`03`.

### V12. A record made before the player id is known is not counted as this device's newest. Note

`LocalCopyFor` returns this launch's record only when its `user_id` matches; a checkpoint
recorded before the id arrives (not on StrataHub, where the id precedes the game) can be
overlooked by the reconcile until the send loop stamps it. Low; documented, not changed.
