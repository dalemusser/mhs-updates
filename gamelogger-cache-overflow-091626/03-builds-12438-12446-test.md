Added 2026-09-28. The builds that carry the new logger were tested the same
way as in `02-reproduction-and-specimen.md`: headless Chromium on the dev
site, signed in as a test member, with the log host blocked in the browser
where noted. Both builds were tested because the `ClassifierIssuesTesting`
collection mixes them:

| Collection unit | Version | Build |
|---|---|---|
| Unit 1, 3, 4, 5 | v2.8.2 | 20260921-12438 |

## The cause: `toSend` is a field in the builds

Both builds contain the drop-in `GameLogger.cs` from this folder. Their
IL2CPP metadata (`global-metadata.dat` in each build's `.data` file) has
every method, field and message unique to it:

- methods `RemoveFromQueue`, `BuildRequestBody`, `WithDevice`,
  `SerializeQueueTrimmed`, `ParseCache` and `MarkCacheDirty`;
- fields `singleSendRemaining` and `batchSize`;
- the `LogCacheOverflow` event and all the drop-in's warnings;
- the same constant values (batch of 50, cache of 512 KB and 1,500
  entries, retry 10 s to 60 s).

The v2.8.1 build has none of these.

One thing differs. In the drop-in, `toSend` is a local, a new list on
every pass of the send loop:

```csharp
while (true)
{
    List<Dictionary<string, object>> toSend = new();   // GameLogger.cs line 350
```

In both builds `toSend` is a **field of `GameLogger`**, along with `logUrl`,
`logAuth`, `logConfig`, `jsonData` and `bodyRaw`. The send coroutine's own
state holds only `retryDelay` and `request`. The v2.8.1 logger already kept
its working variables (`logData`, `jsonData`, `bodyRaw`, `logList`) as
fields, so this matches the existing code style. The list is not emptied
between passes, and that one change produces both defects:

- **Defect A.** After a 2xx, `RemoveFromQueue(toSend.Count)` empties the
  queue, but `toSend` still holds the entries. The next pass finds
  `toSend.Count > 0`, sends the same list again, and appends anything newly
  queued.
- **Defect B.** After a batch 400 the loop switches to single sends
  (`take = 1`). It adds the queue's head to the list that is still full, so
  a batch one entry longer goes out and is refused again. With the wedged
  store the batch starts at 38 entries and reaches 101 after 63 retries.
  The server's ledger shows exactly 63 `entry 0` refusals before the
  batch-size refusals begin.

A line-by-line port of the drop-in's send loop, run against a fake server
(`specimen/send-loop-simulation.py`), confirms it. With `toSend` new each pass, each event is accepted once, and
the wedged store recovers: one refused batch, one refused `{}` sent on its
own, then the 37 events accepted. With `toSend` kept between passes, the
opening events repeat forever, and the wedged store gives the growing
refused batch above.

**The fix is to restore the drop-in's line 350:** a new list, or
`toSend.Clear()`, at the top of every pass. The same goes for any other
per-send state kept in a field. A reused field that still points into the
queue is also the most likely cause of the original `{}`. In v2.8.1,
`logData` is a field, and clearing it for reuse would empty the queued
entry it points to.

## Defect A: an accepted batch is sent again

After a 2xx the entries in that request stay in the batch the loop sends.
The loop sends them again at once, again and again, with anything queued
since added to the batch. The saved cache is emptied, so the problem lives
only in memory and ends when the page closes.

It does not need an outage: it starts as soon as two events are queued
together, which is the start of every session (the two opening events are
logged 17 ms apart). It is already in the log data. On 2026-09-25 three dev
accounts playing these builds, two on Chromebooks and one standalone
Windows build, produced about 680,000 duplicate entries. One Chromebook
account alone produced 272,811 entries of 60 distinct events in two hours.
Its duplicates began with the second request of its first session on the
new build.

**Fix:** `toSend` new each pass (above). The drop-in's removal after a 2xx
is correct once the list is rebuilt every pass.

## Defect B: a refused batch is resent at once, forever

With the store that the schools' build (v2.8.1) leaves on a wedged device,
the sequence is:

1. The cache loads with its `{}` first.
2. The device block is attached to that entry at send time, so entry 0 of
   the batch is `{"device":{…}}` with no `user_id`.
3. The server refuses the whole batch: 400
   `entry 0: missing or invalid 'user_id' field`.
4. About 100 ms later the same batch goes again, with one more
   `{"device":{…}}` entry added. The body grows by exactly 318 bytes per
   retry, the size of one device block.
5. After about 60 retries the batch is over 100 entries, and every request
   is refused with 400 `Batch size exceeds maximum of 100`.
6. The body keeps growing: 20.6 KB to 144 KB in 38 s, at about 11
   requests per second.

Nothing is ever recorded. The `{}` stays first in the store, so this
repeats on every launch.

The same pattern shows in the standalone build's session of 2026-09-25,
with an ordinary bad entry rather than the `{}`: 57 refusals of
`entry 43: missing or invalid 'user_id' field`, then 1,511
`Batch size exceeds maximum of 100` in six minutes. Any entry without a
`user_id` triggers it. The schools' build logs a debug-menu event before
identity is set, and one of those sits in the wedged specimen.

**Fix:** the same one. The drop-in already caps batches at 50 and
isolates a refused entry by sending one at a time (`singleSendRemaining`).
Both stop working when `toSend` carries over between passes.

**Hardening we recommend alongside it,** so a future slip cannot flood the
server:

1. When loading the cache, drop entries that have no fields or no
   `user_id`. The `{}` left by v2.8.1 then never goes out.
2. Pause briefly, about a second, after a 400 or 413 before the next
   request. Today those paths continue at once, which is correct only
   while every pass makes progress.
3. Remove sent entries by identity rather than by count: dequeue while the
   head is one of the entries just sent. A stale or mismatched `toSend`
   then removes nothing it did not send.

## Devices already wedged by the schools' build

With either new build as it stands, a wedged device does not recover (the
last row of the results). Its site data still has to be cleared, as now.

With the fix, no clear is needed. The first launch of the fixed build
refuses the `{}` once, drops it, and sends what is behind it (with
hardening 1, the `{}` is dropped on load without a request). Those entries
carry the student's own `user_id`, so they are recorded under the right
student. Entries with a null `user_id` are dropped by the same rule.

## Verifying the next build

1. **Normal play for a minute:** every event reaches the server once, and
   when the game is idle it makes no requests. For the test account, the
   number of entries equals the number of distinct (event type, timestamp)
   pairs. The verification in `01-…` (step A) checks only for `201`
   replies and would pass a build with defect A; use this check instead.
2. **Block the log host for two minutes, then unblock:** the backlog
   arrives once, the store empties, and the request rate drops back to
   normal.
3. **Load a wedged store before launch** (either `specimen/` file below
   goes into IndexedDB `/idbfs`, store `FILE_DATA`, at
   `/idbfs/<hash>/PlayerPrefs`, where `<hash>` is the MD5 of the play
   page's URL up to its last `/`): the first launch drains it with no 400
   loop.
4. **A batch with one entry lacking `user_id`:** that entry is dropped
   once, the others are recorded, and no loop follows.
