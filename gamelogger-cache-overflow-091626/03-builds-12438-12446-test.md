## Defect A: an accepted batch is sent again

After a 2xx the entries in that request stay in the batch the loop sends.
The loop sends them again at once, again and again, with anything queued
since added to the batch. The saved cache is emptied, so the problem lives
only in memory and ends when the page closes.

It does not need an outage: it starts as soon as two events are queued
together, which is the start of every session (the two opening events are
logged 17 ms apart). It is already in the log data. On 2026-09-25 three dev
accounts playing these builds, two on Chromebooks and one standalone
Windows build, produced about 680,000 duplicate entries. One Chromebook
account alone produced 272,811 entries of 60 distinct events in two hours.
Its duplicates began with the second request of its first session on the
new build.

**Required:** after a 2xx, remove from the queue exactly the entries that
were in that request, then persist the queue. Never resend an accepted
entry.

## Defect B: a refused batch is resent at once, forever

With the store that the schools' build (v2.8.1) leaves on a wedged device,
the sequence is:

1. The cache loads with its `{}` first.
2. The device block is attached to that entry at send time, so entry 0 of
   the batch is `{"device":{…}}` with no `user_id`.
3. The server refuses the whole batch: 400
   `entry 0: missing or invalid 'user_id' field`.
4. About 100 ms later the same batch goes again, with one more
   `{"device":{…}}` entry added. The body grows by exactly 318 bytes per
   retry, the size of one device block.
5. After about 60 retries the batch is over 100 entries, and every request
   is refused with 400 `Batch size exceeds maximum of 100`.
6. The body keeps growing: 20.6 KB to 144 KB in 38 s, at about 11
   requests per second.

Nothing is ever recorded. The `{}` stays first in the store, so this
repeats on every launch.

The same pattern shows in the standalone build's session of 2026-09-25,
with an ordinary bad entry rather than the `{}`: 57 refusals of
`entry 43: missing or invalid 'user_id' field`, then 1,511
`Batch size exceeds maximum of 100` in six minutes. Any entry without a
`user_id` triggers it. The schools' build logs a debug-menu event before
identity is set, and one of those sits in the wedged specimen.

**Required:**

1. Send at most 100 entries per request (the server's limit).
2. On a 400, do not resend the same batch. The server names the bad entry
   (`entry N: …`): drop that entry and send the rest. If it cannot be
   identified, drop the batch.
3. Back off on every failure, HTTP or network: no retry sooner than a few
   seconds, growing with repeated failures. The network-failure backoff in
   these builds is fine; apply the same to HTTP errors.
4. When loading the cache, and again before sending, drop entries that have
   no fields or no `user_id`. Never attach the device block to such an
   entry.
5. Do not add an entry per attempt (the `{"device":{…}}` entries in step 4).

## Devices already wedged by the schools' build

With either new build as it stands, a wedged device does not recover (the
last row of the results). Its site data still has to be cleared, as now.

With required change B.4 in place, no clear is needed. The first launch of
the fixed build drops the `{}` and sends what is behind it. Those entries
carry the student's own `user_id`, so they are recorded under the right
student. Entries with a null `user_id` are dropped by the same rule.

## Verifying the next build

1. **Normal play for a minute:** every event reaches the server once. For
   the test account, the number of entries equals the number of distinct
   (event type, timestamp) pairs.
2. **Block the log host for two minutes, then unblock:** the backlog
   arrives once, the store empties, and the request rate drops back to
   normal.
3. **Load a wedged store before launch** (either `specimen/` file below
   goes into IndexedDB `/idbfs`, store `FILE_DATA`, at
   `/idbfs/<hash>/PlayerPrefs`, where `<hash>` is the MD5 of the play
   page's URL up to its last `/`): the first launch drains it with no 400
   loop.
4. **A batch with one entry lacking `user_id`:** that entry is dropped
   once, the others are recorded, and no loop follows.
