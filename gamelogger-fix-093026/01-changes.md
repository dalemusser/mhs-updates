# The logging fix: what changed, and how it was verified

**Version:** 1.2 (2026-10-01; version 1.0 on 2026-09-30, 1.1 after review the same day, 1.2 the same night).
**Base:** the game team's project copy of 2026-09-28 (`20260928_CH12449_MHS 2.0`, the logger of builds 20260921-12438 and 20260925-12446), Unity 6000.0.74f1.
**Files:** `Game-Code/Systems/Logging/GameLogger.cs` and `Game-Code/Systems/Logging/LoggingData.cs`, mirroring `Assets/Scripts/Systems/Logging/`, plus `Game-Code/Systems/Save Load System/SettingsSaveManager.cs` for the console error of §8 (mirroring `Assets/Scripts/Systems/Save Load System/`). Nothing else changes: no prefab, asset, scene or host-page edit, and the public API of `GameLogger` (`Instance`, `LogEvent`, `SendToServer`, `SetUserId`, the eight `Log…Event` wrappers, `IsSendingLogs`, the `ICheckForUnitTransition` members) is the same. `AuthManager.cs` is unchanged.

The defects are numbered as in `00-plan.md` and as G1–G6 in `stratahub/docs/mission-hydrosci/mhs-game-logging-issues-092826.md`.

## The changes, defect by defect

### 1 and 2. Per-send state kept in fields (G1)

The 2026-09-14 build (v2.8.1) emptied the queued entry with `logData.Clear()` and then read the empty entry as an empty queue, so one request failing twice stopped all sending on that browser profile. The 2026-09-25 logger kept the batch list `toSend` as a field and never cleared it, so every accepted batch was sent again (about 8 requests a second, from the second request of every session) and a refused batch grew by one entry and was refused again, forever.

**Change.** Every per-send value is local to the send coroutine: the batch list is a new list at the top of every pass, and the request body, the request and the endpoint config are locals. The fields `logData`, `toSend`, `jsonData`, `bodyRaw`, `logUrl`, `logAuth`, `logConfig` and `logList` are gone, with the commented-out code that used them. The loop exits only when the queue is empty.

### 3. Queued entries' details overwritten by later events (G2)

Each `LoggingData` entry kept one dictionary, cleared and refilled it on every event, and handed that same object to the logger, which stored the reference in the queued entry. While an entry waited to be sent, the next event from the same component overwrote its details. `LogPlayerPositionEvent` reused two dictionaries the same way. The "variable" entries also stored the Soap variable objects, not their values.

**Change.** `LoggingData.ExecuteLogData` (both entry kinds) builds a new dictionary per call, and the variable entries add the variable's current `Value`. `LogPlayerPositionEvent` builds new dictionaries per call. As a backstop, `GameLogger.LogEvent` stores a copy of the caller's data (nested dictionaries and lists copied too), so no caller can change a queued entry.

The shape of `data` does not change for any event type in use: the only assets with variable entries are the map's, whose events go through `LogTopoMapEvent` (unchanged). If a variable entry is ever logged through the generic path, `data` now carries the value where it used to carry a serialized `ScriptableObject`.

### 4. The first event of a session has no user id (G4)

The debug-menu controller logs before `AuthManager` has called `SetUserId` (in release builds it destroys itself in `Awake` under `NO_DEBUG`, and `OnDestroy` logs a "closed" event), so the entry went out with `user_id: null` and was refused.

**Change.** `SetUserId` stamps the id onto every queued entry that has none, and the send loop does not send an entry that lacks only its user id while the id is unknown: it waits (one look per second, no request). The entry goes out with the id in the session's first batch. The cached backlog from earlier sessions, which carries ids, is sent meanwhile. If a session never learns its identity, its id-less entries stay in the cache and are dropped on the next launch (below).

### 5. Two logger instances (G5)

Both core-systems prefabs carry a `GameLogger` on the console-manager object, `Awake` never assigned `_instance`, and the duplicate check destroyed the shared game object.

**Change.** `Awake` assigns `_instance`; a second component removes only itself (`Destroy(this)`) and does nothing else. `isSendingLogs` is an instance field (`IsSendingLogs` reads it from the instance), so a lost instance can never strand the flag. `OnDestroy` clears `_instance` and flushes the cache. The `Instance` getter still creates a logger if none exists, with a warning; console printing tolerates its unassigned debug-log setting.

### 6. Hardening (G3)

- **Load:** an entry with no fields, no `eventType` or no `user_id` is left out of the queue when the cache is loaded (with one warning giving the count), and the cleaned queue is written back at once. The `{}` that v2.8.1 leaves behind, and the id-less debug-menu entries of older builds, never produce a request.
- **Before sending:** the same rule at the head of the queue and when a batch is built (an unsendable entry ends the batch and is dropped on the next pass). The device block is only ever attached to entries that are sent.
- **Removal by identity:** after a 2xx (or a 400/413 on a single entry) the queue is dequeued while its head is one of the entries just sent. Entries the cache trimming dropped during the request are simply gone; entries that were not sent are never removed.
- **Pause after a refusal:** one second after a 400 or 413 before the next request.
- **Request timeout:** 30 s, after which the attempt counts as a failure and backs off.
- **Batches:** at most 50 entries (the server's limit is 100), unchanged.
- **The bounded cache, coalesced writes and backoff** (10 s doubling to 60 s) from the 2026-09-16 drop-in stay as they were.
- **Unit transitions:** `CallToTransitionToNextUnit` reports ready when the queue is empty, when no send is running, or five seconds after the transition first asked; it flushes the cache when it says yes. With retry-forever, waiting on the logger without a limit would hold a unit change for as long as the log service is unreachable. Whatever is still queued is persisted and sent by the next unit's build.
- **Endpoint:** the hard-coded fallback to the legacy `/logs` route and API key is removed. The endpoint comes from the host page through `MHSBridge`; if it is missing the loop waits and looks again every five seconds, and nothing is lost. An exception inside the coroutine can no longer leave `isSendingLogs` set (`try/finally`).

### 7. Smaller things

- `IsNetworkAvailable()` stays as an advisory check with a comment; nothing depends on it.
- The build's version string: set `bundleVersion` in the release build profile (the test build used `20260930-logfix`); the pipeline's `-changelistNum` argument names the report file only.
- The console errors seen in headless runs are covered in the verification below.

### 8. The settings load's `null` body (G6, the console error)

`SettingsSaveManager.LoadSettingsCoroutine` posts to the save service's `/api/settings/load` and, on a 2xx reply, hands the body to `JsonUtility.FromJson<SettingsResponse>`, expecting `null` back when the player has no saved settings. The service answers `200` with the body `null` in that case, and `JsonUtility.FromJson` throws `ArgumentException: JSON must represent an object type.` for `null`, `[]` or any non-object body (it returns `null` only for an empty string). So for every player without a settings record the coroutine died at that line on every scene load: once in the main menu, twice on entering a unit (the gameplay scene has a second `AuthManager`, and each raises the load-settings event on a new scene).

**Change.** Before parsing, an empty or `null` body counts as "no settings" (the existing "No settings found, using defaults" branch); any other body that `JsonUtility` cannot parse is reported through the debug console and counts as a failed load, so no body can end the coroutine.

**Side effects, checked.** The only listener of the load callback is `LoadSettingsFromDatabase`, which prints "Settings loaded!" or "Failed to load settings" to the in-game debug console (shown only with debug logs enabled); nothing else in the code reads the result. The "no settings" branch does not call `ApplySettings`, so the settings variables keep their defaults, exactly the state the dying coroutine left behind. Players with saved settings get an object body and parse as before. The load-settings event itself has no other code listeners, so nothing else changes its behaviour. What is new for players without settings is only that the coroutine completes and the debug console gets its "Failed to load settings" line instead of an exception.

## Version 1.1 (2026-09-30, after review)

Two independent reviews of version 1 (one for logic and concurrency, one for Unity, IL2CPP and WebGL behaviour) found no show-stopper; the core mechanics held under adversarial tracing. These changes to `GameLogger.cs` and `LoggingData.cs` came out of them; `SettingsSaveManager.cs` is unchanged.

- **Real-time waits.** All six waits in the send loop are `WaitForSecondsRealtime`. The game sets `Time.timeScale = 0` in its pause and unfocused states, and a scaled wait (a backoff, the identity poll, the pause after a refusal) could not elapse while the game was paused, so events logged during a pause queued up until it ended. Nothing was lost, but sending stalled.
- **Serialization guarded.** Building a request body and serializing the cache are wrapped: if Newtonsoft cannot serialize an entry (a value with a throwing getter, a `UnityEngine.Object` handed to `SetValues`), the offending entry is found by serializing the candidates one by one, dropped with a warning, and the loop continues after the usual pause; if no single entry is at fault the oldest candidate goes so the loop still makes progress. Before, such an entry ended the coroutine and threw out of every later `LogEvent` whose cache write fell outside the two-second window, into the component that logged. No current caller passes such a value; this is the rule "nothing unsendable goes out" applied to serialization.
- **Identity from the bridge** (WebGL player builds only). While the head of the queue waits for a user id, the loop asks `MHSBridge` for the id the host page supplied before the game started, and calls `SetUserId` with it instead of waiting for `AuthManager`'s first identity fetch. Same source of truth, no dependence on timing; in the Editor and standalone builds `AuthManager` stays the only source.
- **Small guards.** A quitting flag stops the `Instance` getter from creating a logger during teardown (components that log from their own `OnDestroy` would otherwise resurrect one, with an Editor warning); `Vector3VariableEntry` checks `Instance` for null like every other caller. `OnDisable` clears the sending flag if the game object was deactivated, since a stopped coroutine never runs its `finally`. The cache loader appends anything already queued behind the cached entries instead of clearing it. The batch size grows back after a success once a 413 has halved it. The transition gate treats a gap of over a second since its last call as a new request, so a previous transition that never changed scene cannot leave it stale. In `LoggingData`, the two variable-entry `eventKey` paths use the variables' values, `Vector3VariableEntry` passes a zero vector for an unassigned variable instead of dereferencing it, and `Vector2`/`Vector3` values on the generic paths are written as `{x, y, z}` objects, the shape the position and map wrappers already use.

Accepted as is: `LogEvent`'s copy covers dictionaries and lists, not arbitrary objects (no caller passes any); the overflow report can over-count entries the cache trimmed while a request was in flight; a server `max_batch_size` below 50 would make batches cycle through single sends rather than loop; the removed fallback only matters for a page with no bridge config, which has no identity either; the 30-second timeout makes delivery at-least-once if the server answers very late. The settings file is delivered with LF line endings while the original is CRLF, so a whole-file diff appears unless the team's VCS normalises line endings.

## Version 1.2 (2026-09-30/10-01, additions for the server side)

Four additions to `GameLogger.cs`, all additive: no existing field or behaviour changes, and the log service already stores unknown top-level fields as received. They exist because a game build is expensive to make and test, and these let the server side improve later without another one.

- **`session_id`, `seq`, `entry_id`** on every entry: one id per launch of the game, a per-session counter, and `"<session_id>:<seq>"`. The server can add a unique index and de-duplicate (exactly-once delivery), see gaps, and order entries independently of the device clock; analysts have a hard key per entry.
- **`recovered: true`** on every entry loaded from the saved cache, so an entry sent after a reload or an outage is distinguishable from a live one (the grader and the research partner can treat it accordingly). Entries keep the `session_id` of the session that logged them.
- **`sent_at`** on every sent copy (not persisted): with the server's received time this measures a device's clock skew.
- **`429` with `Retry-After`** is honoured as a pause of that length (clamped to 1–300 s), otherwise the current backoff; so a server-side rate limit can set the pace. On WebGL the header is readable only if the service exposes it for cross-origin responses (`Access-Control-Expose-Headers: Retry-After`); without that the client falls back to its backoff, which also works.

What the server side can do with these, without a game change: a unique index on `(game, user_id, entry_id)` with repeats ignored; queries that exclude or mark `recovered` entries; a per-account rate limit answering `429`; clock-skew reports from `sent_at` against `serverTimestamp`. These are listed in `02-logging-redesign-if-starting-over.md` §8.

**The console error `ArgumentException: JSON must represent an object type.`** Cause found 2026-09-30 and fixed in §8 (verified in row 8). `SettingsSaveManager.LoadSettingsCoroutine` posts to the save service's `/api/settings/load` and, on a 2xx, calls `JsonUtility.FromJson<SettingsResponse>(www.downloadHandler.text)` expecting `null` back when the player has no saved settings. The service answers `200` with the four-byte body `null` in that case (checked for the test member and for an unknown id), and `JsonUtility.FromJson` throws this exception for `null`, `[]` or any non-object body (confirmed in the editor); it returns `null` only for an empty string. So for every player without a settings record the load coroutine dies at that line on every scene load: the "No settings found, using defaults" branch and the callback never run. Defaults apply anyway, so the only visible effect is the console error, but anything that waits on that callback never hears back. It appears once in the main menu and twice on entering a unit because the gameplay scene has a second `AuthManager` and each one raises the load-settings event on a new scene. Fix (one place): treat an empty or `null` body as "no settings" before parsing, for example `var text = www.downloadHandler.text; response = string.IsNullOrWhiteSpace(text) || text.Trim() == "null" ? null : JsonUtility.FromJson<SettingsResponse>(text);`. `GameSaveManager`'s state load is not affected: it wraps the array the state endpoint returns. The play page's own crash reporter posts a `crash` entry to the log service when the headless browser refuses pointer lock (`unhandled_rejection: The root document of this element is not valid for pointer lock`); that is one extra request per session in these tests and belongs to StrataHub, not the game.

**Building on a fresh checkout.** The first build of the 2026-09-28 copy failed with 136 compile errors: `Assets/Imported/Samples/StarterAssets/InputSystem/PlayerInputs.inputactions` has *Generate C# Class* on with the wrapper path `Assets/Third Party/StarterAssets/InputSystem/PlayerInputs.cs`, a folder the zip does not contain, so the first import generated a second `PlayerInputs` class next to the checked-in one. The test copy removed the generated file and turned generation off for that asset; the team's own machines never re-import it. Worth fixing in the mainline before a CI build from a clean workspace. Also: the team's `BuildFromBuildProfiles` opens a folder dialog in a static initializer; in batch mode Unity cancels it with a warning, harmless.
